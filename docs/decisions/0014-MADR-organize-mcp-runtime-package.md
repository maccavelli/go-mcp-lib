# Organize MCP packages by capability and dependency ownership

## Context and Problem Statement

The owner requested a renewed assessment of `go-selfupdate-lib`,
`go-llmprovider-lib`, `go-tui-lib` and `acp-go-sdk2` before approving the
runtime relocation. The local provider checkout is named `go-llmprovider-sdk`;
that is the repository assessed here.
[0013-REPORT-library-package-layout-assessment.md](../reports/0013-REPORT-library-package-layout-assessment.md)
records all four layouts. Three keep Go source out of the root. ACP retains a
root `acp` package, with functional helper packages beside it. Their shared
principle is package ownership by capability, with private mechanisms and
colocated tests; neither an empty root nor a public command package is universal.

`go-mcp-lib` has twelve production files and twelve tests at its root, all
belonging to `mcp` or its external tests. It already separates `codec/` and
`protocol/`. The question is how to complete that functional organization
without mistaking directories for independent APIs.

Moving Go source into a directory changes its package import path. Splitting
the runtime into multiple public packages would also affect access to private
state and the sealed request/transport interfaces. A file-only grouping must
not accidentally become a larger API redesign or expose SDK runtime objects.

## Decision Drivers

* Keep the repository root free of Go source and test files.
* Follow the fleet's functional packages and explicit dependency direction.
* Preserve the cohesive runtime API, behavior and SDK isolation.
* Scope private helpers to their actual owners and keep tests with those owners.
* Retain both existing module boundaries and every qualification obligation.
* Keep other repositories read-only and make the import migration explicit.

## Considered Options

* A — Functional packages with a cohesive `mcp/` runtime and scoped internals.
* B — Preserve the root import through a thin facade over private packages.
* C — Introduce separate public server, client and transport packages.

## Decision Outcome

Chosen option: "A — Functional packages with a
cohesive `mcp/` runtime and scoped internals", because it applies the four
repositories' ownership pattern while preserving the existing runtime seams.
It explicitly maps each current component rather than proposing subdivisions
based on file count. The owner accepted this revised decision and approved
execution of its PLAN on 2026-11-27.

### Package ownership

| Path | Responsibility and disposition |
| :--- | :--- |
| `mcp/` | Move the twelve root production files and twelve tests together. Own server/client handles, sessions, requests, middleware, tool/resource registration, runtime transport wrappers and output-validation policy. Keep `package mcp` / `mcp_test` and private seams intact. |
| `mcp/internal/sdkbridge/` | Move the current `internal/sdkbridge/` implementation and tests. Its production importers are runtime files only; narrowing the internal boundary expresses that ownership. Update its import identity and every test/plant locator. |
| `codec/` | Retain the independent strict raw-JSON API and its tests. Do not move it under the runtime or copy its checks into another package. |
| `protocol/` | Retain generated wire DTOs, generated validation support and contract artifacts. The pending R2/R3 candidate owns its publication; this layout change must not alter generated bytes. |
| `internal/validation/` | Retain the canonical schema validator and its tests/fixtures at the common root scope. Runtime output policy uses it, and the R2/R3 generator emits protocol support that imports it. It is not runtime-only. |
| `cmd/mcpgen/` | Retain the existing separate generator module and its command entry point, internal acquire/model/emit/qualify/publication packages, tests and fixtures. This is maintainer tooling, not an application library import. |
| `schema/`, `scripts/`, `tools/`, `docs/` | Retain generation inputs, local gate tooling, inventories and documentation in their existing roles. |

Canonical consumer imports are `github.com/maccavelli/go-mcp-lib/mcp`,
`github.com/maccavelli/go-mcp-lib/codec` and
`github.com/maccavelli/go-mcp-lib/protocol`, according to the capability needed.
There is no root compatibility facade, `pkg/` wrapper or repository-name
directory. No consumer-facing API lives under `cmd/`. No new Go module or
exported identifier is introduced by this migration.

The observed command layouts differ legitimately: self-update and provider
maintenance tools use scoped `internal/cmd/`, while ACP has a separate
`cmd/generate` module. Go's `cmd` convention names executable tools. It does
not make `cmd` an import path for their library APIs, nor require relocating
the existing MCP generator to make the runtime functional.

### Dependency and test rules

* Keep the runtime cohesive: `Transport.transport` and `Request.ownedRequest`
  seal package-private contracts, while handles and middleware share private
  state. Server/client/transport directories would require a separate owned
  contract design; they are not implied by the number of files.
* Preserve downward imports: `mcp` consumes `protocol`, its private bridge and
  shared validation; generated protocol support consumes shared validation.
  Neither `codec` nor `protocol` imports `mcp` or its bridge. The bridge must
  not import its owning runtime and create a cycle.
* Place private mechanisms under the smallest common owning subtree. A helper
  shared by independent public packages belongs at root `internal/`; a helper
  used only within `mcp` belongs under `mcp/internal/`. Avoid generic `util`
  packages and duplicate validator implementations.
* Keep unit and external consumer tests beside the owning package; keep
  fixtures under its `testdata/`. Preserve generator integration tests where
  they exercise generator behavior. Add public test-support packages only for
  an actual supported consumer use case, not to collect internal tests.
* Introduce future capability/adaptor packages only with a cohesive purpose
  and an acyclic owned API. Adapters may depend on the core they adapt; the
  core must not depend on those adapters. Do not create empty package stubs.
* Keep package and module decisions separate. A nested module needs an
  independent dependency or release boundary, as with the provider's
  `authcontract` or ACP's generator, not just another directory.

## Consequences

* Good, because public capabilities and private ownership are discoverable in
  the package tree and follow the same principles as the four reference repos.
* Good, because tests, private interfaces and SDK isolation retain their package
  semantics without forwarding layers.
* Good, because schema generation and the generator module retain independent
  identities and qualification boundaries.
* Good, because the runtime-only bridge is inaccessible to unrelated sibling
  packages under Go's `internal` import rule.
* Bad, because existing consumers must change their runtime import path.
* Bad, because inventories, examples, source locators and migration documentation
  need a coordinated update; moving source alone is insufficient.

## Confirmation

Confirm an empty root Go inventory, one canonical public runtime package,
unchanged public declaration coverage apart from its recorded package identity,
unchanged generated hashes and complete module/target qualification. Every new
layout assertion must reject its deliberately broken scratch input. Existing
SDK-exposure and middleware/candidate bypasses must still be caught at their
new locations, including the owned-decoder plant in the moved bridge. Test the
proposed dependency rules against forbidden imports in scratch, including a
sibling package trying to import `mcp/internal/sdkbridge`. A clean
`go test ./...` selection must discover the moved tests, with module inventories
proving that generator tests have not disappeared across its nested boundary.

## Pros and Cons of the Options

### A — Functional packages with scoped internals — recommended

* Good, because it meets the requested layout with a focused package migration.
* Good, because the existing sealed interfaces and shared state remain private.
* Good, because private scope and existing independent capabilities are explicit.
* Bad, because moderate migration work includes runtime/bridge imports,
  inventories, qualification locators and consumer guidance.

### B — Root facade

* Good, because existing imports could remain valid.
* Bad, because Go files remain at the root, contrary to the selected requirement.
* Bad, because forwarding or alias layers add API and maintenance work.
* Neutral, because retaining a root API is valid Go, as ACP demonstrates; it
  does not satisfy the owner's MCP empty-root requirement.

### C — Multiple public runtime packages

* Good, because it offers additional explicit public boundaries.
* Bad, because it requires an acyclic contract/implementation design and changes
  private seams, giving it the highest design/migration cost. The reference
  repositories do not establish a requirement to split cohesive core types.

## More Information

The reference assessments and source locators are retained in
[0013-REPORT-library-package-layout-assessment.md](../reports/0013-REPORT-library-package-layout-assessment.md).
This decision changes the runtime placement described by
[0002-MADR-build-schema-driven-mcp-framework.md](0002-MADR-build-schema-driven-mcp-framework.md),
after its R2/R3 prerequisite, while retaining its protocol, runtime isolation,
generation and native-validation obligations. It authorizes no consumer-repo
mutation, upstream-forge change, push, tag or history rewrite.

Go's [module-layout guide](https://go.dev/doc/modules/layout) permits root
library packages and separates commands from importable library packages.
Its [code-organization guide](https://go.dev/doc/code#Code_organization)
defines packages by directory and import paths by module plus subdirectory.
The [package-naming guidance](https://go.dev/blog/package-names) supports clear,
cohesive names. None mandates a universal fleet directory tree or file limit;
the empty-root constraint is the owner's choice for this repository.
